# Запрос к 7RL: публиковать фазу как состояние, а не только как события

Небольшая добавка к телеметрии 7RL Rohan Trade System. Нужна дашборду, чтобы
показывать фазы по всем 22 символам. **Ничего не удаляет и не меняет в
существующем поведении, торговых путей не касается.**

## Что не так сейчас

`phase_changes_total` — счётчик **переходов**. Он срабатывает только в момент
смены доминирующей фазы (`system_loop.py`, цикл по символам):

```python
prev_phase = self._last_dominant_phase.get(symbol)
if prev_phase is not None and prev_phase != phase_output.dominant_phase:
    inc_phase_changes(symbol, prev_phase, phase_output.dominant_phase)
```

Отсюда два следствия для любого внешнего потребителя:

1. **Пока режим держится, метрика молчит.** Отличить «фаза не менялась» от
   «данных нет» снаружи невозможно. За 21.08 BTC простоял в `uptrend` 49 часов
   подряд — за это время не выгрузилось ни одной строки `phase_changes_total`,
   и дашборд не мог узнать текущую фазу вообще ни по одному символу.
2. **`_last_dominant_phase` живёт в памяти процесса.** При рестарте счётчики
   начинаются с нуля, и тот, кто восстанавливает состояние из их приращений,
   теряет по переходу на каждый перезапуск. За 17–21.08 процесс стартовал 25 раз.

Восстанавливать состояние из потока событий в таких условиях в принципе
ненадёжно — сколько ни чини потребителя.

## Что предлагается

Три gauge-метрики, которые **переизлагают текущий `PhaseOutput` на каждом тике**:

| метрика | лейблы | значение |
|---|---|---|
| `phase_probability` | `symbol`, `phase` | элемент `phase_probs` (5 рядов на символ) |
| `phase_confidence` | `symbol` | `PhaseOutput.confidence` |
| `phase_vol_regime` | `symbol` | индекс в `VOL_REGIMES`: 0=low, 1=normal, 2=high, -1=unknown |

Gauge переизлагается при каждом флаше экспортёра, поэтому не зависит ни от
стабильности рынка, ни от перезапусков.

Доминирующая фаза — это argmax `phase_probability`, отдельный ряд под неё не
нужен. Специально **нет** лейбла с названием фазы на `phase_confidence`: иначе
при каждой смене фазы появлялся бы новый ряд, а старый оставался бы висеть со
устаревшим значением. При такой схеме на символ приходится ровно 7 рядов, и все
они обновляются каждый тик.

## Как применить

```sh
cd /home/rohan/7RL-rohan-trade-system
python3 apply_phase_gauge.py --check     # проверить, что все анкеры на месте
python3 apply_phase_gauge.py             # применить, рядом лягут .bak
# перезапустить сервис — метрики появятся в state/metrics.jsonl
```

Откат: `python3 apply_phase_gauge.py --revert`.

Скрипт правит три файла по точным фрагментам, а не по номерам строк, и
**отказывается писать**, если хоть один фрагмент не найден или найден дважды.
Повторный запуск тоже отказывает. Перед записью делает `.bak`.

Затрагиваются:

- `src/telemetry/metrics.py` — три поля в `_Instruments`, три `create_gauge`,
  функция `set_phase_output`, строка в `__all__`
- `src/telemetry/__init__.py` — реэкспорт `set_phase_output`
- `src/services/system_loop.py` — импорт и один вызов сразу после
  `self._last_dominant_phase[symbol] = ...`

Новых импортов не добавляется: порядок фаз и коды vol-режимов продублированы
локальными константами в `metrics.py` (если удобнее — замените на импорт
`PHASES` / `VOL_REGIMES` из `src.contracts._constants`).

Проверено на макете структуры: применяется, даёт валидный Python, откатывается,
отказывается при повторе и при несовпадении анкера. Уникальность всех восьми
анкеров в текущих исходниках 7RL подтверждена.

## Что это даёт дашборду

- сетка `phases · 22` оживает целиком (сейчас в ней 1 живая ячейка из 22);
- детектор показывает настоящее распределение вероятностей вместо флага «100%»;
- появляется `vol_regime`, который сейчас всегда захардкожен в `normal`;
- дашборд перестаёт зависеть от `phase_changes_total` и от частоты перезапусков.

Сторона дашборда уже готова: `shims/phase_shim.py` подхватывает эти метрики
автоматически, как только они появятся, и до тех пор работает по-старому.
