# 3 уровня памяти Claude в Obsidian

Инструкция для настройки системы непрерывной памяти между сессиями Claude через Obsidian-vault. Проверено на проекте Solbot (см. ниже пример структуры).

## Зачем 3 уровня

Claude забывает всё между сессиями. Чтобы работать над долгим проектом, нужна **внешняя память**. Три уровня — три горизонта:

1. **Оперативная** (что делаем сейчас, короткая память) → `auto memory` Claude
2. **Рабочая** (текущие приоритеты, свежая сессия, недавние решения) → Obsidian `00-home/` + `sessions/`
3. **Долгосрочная** (knowledge base: решения, баги, архитектура) → Obsidian `knowledge/`, отдельные специализированные vault'ы

Разделение по **частоте обновления** и **продолжительности жизни**:

| Уровень | Где | Обновляется | Живёт | Объём |
|---|---|---|---|---|
| 1 — Оперативная | auto memory Claude | каждая сессия | до осознанной чистки | ~10 файлов |
| 2 — Рабочая | SolbotVault (home + sessions) | каждая сессия | до квартала | десятки |
| 3 — Долгосрочная | knowledge + специализированные vault'ы | при крупных решениях | навсегда | сотни |

## Уровень 1 — Оперативная память (Claude auto memory)

**Где**: встроенная `auto memory` Claude Code, файлы в `~/.claude/projects/<project>/memory/`.

**Что хранить**:
- Кто пользователь (роль, экспертиза, как работать)
- Доступы (сервер, репозиторий, ключи — без секретов)
- Feedback-правила ("не делай X", "всегда делай Y")
- Ссылки на внешние системы (Obsidian vault, GitHub, Linear)
- Краткие pointer-ы на активные задачи

**Что НЕ хранить**:
- Подробности решений (они в Уровне 3)
- Логи сессий (они в Уровне 2)
- Код, архитектуру (это в проекте или Уровне 3)

**Структура**:
```
~/.claude/projects/<project>/memory/
  MEMORY.md                      ← индекс (всегда загружается в контекст)
  user_expertise.md              ← роль, экспертиза
  project_server.md              ← где развёрнут проект
  project_status.md              ← живой статус проекта
  feedback_session_workflow.md   ← правила работы
  feedback_save_workflow.md      ← что делать при "сохрани всё"
  ...
```

**Формат файла памяти**:
```markdown
---
name: feedback_session_workflow
description: При старте сессии читать ВСЕ слои памяти. При "продолжаем" — подхватить контекст без вопросов.
type: feedback
---

## Правило
При старте новой сессии ОБЯЗАТЕЛЬНО:
1. Прочитать CLAUDE.md (автоматически)
2. Прочитать все файлы из memory/
3. Прочитать 00-home/index.md и текущие приоритеты.md из vault
4. Прочитать последние 2-3 сессии из sessions/

**Why:** пользователь ведёт непрерывную работу. Без чтения сессий — потеря контекста.
**How to apply:** при "продолжаем" подхватить без вопросов, прочитать vault.
```

**Индекс `MEMORY.md`** — одна строка на файл, 150 символов:
```markdown
- [User expertise](user_expertise.md) — трейдер, узлы сигналов — основная зона работы
- [Server deploy](project_server.md) — VPS 62.60.232.247, SSH ключ настроен
- [Project status](project_status.md) — полный статус: 3 бота live, фаза 2 миграции карточек
- [Session workflow](feedback_session_workflow.md) — при старте читать vault, при "продолжаем" — без вопросов
```

## Уровень 2 — Рабочая память (Obsidian vault, home + sessions)

**Где**: основной Obsidian vault, 2 папки:
- `00-home/` — постоянно актуальное
- `sessions/` — лог каждой встречи

**`00-home/` структура**:
```
00-home/
  index.md                    ← карта vault (ссылки на ключевые заметки)
  текущие приоритеты.md       ← ЖИВОЙ список задач, обновляется каждую сессию
```

**`00-home/index.md`** — главная точка входа:
```markdown
---
tags: [home, index]
date: 2026-04-15
---

# Проект — Knowledge Vault

Краткое описание проекта.

## Архитектура
- [[архитектура — N сервисов на VPS]]
- [[основные компоненты]]

## Ключевые решения
- [[решение 1]]
- [[решение 2]]

## Текущие приоритеты
→ [[текущие приоритеты]]
```

**`00-home/текущие приоритеты.md`** — самый важный файл Уровня 2:
```markdown
---
tags: [priorities, active]
date: 2026-04-15
---

# Текущие приоритеты

## Следующая сессия
1. **Задача А** — краткое описание, ссылка на детали
2. **Задача Б** — ...

## Завершено (2026-04-15) — <тема сессии>
- кратко что сделано
- → [[knowledge/decisions/ключевое-решение]]

## Завершено (2026-04-14) — ...
- ...

## Сделано (ссылки на сессии)
→ [[сессия 2026-04-14 тема]]
→ [[сессия 2026-04-15 тема]]
```

**`sessions/`** — отчёт за каждую значимую встречу:
```
sessions/
  сессия 2026-04-14 <краткая тема>.md
  сессия 2026-04-15 <краткая тема>.md
```

**Формат сессии**:
```markdown
---
tags: [session]
date: 2026-04-15
---

# Сессия 2026-04-15 — <тема>

## Контекст
Что было до, зачем встреча.

## Что сделано
### Модуль / фича 1
- конкретные шаги
- файлы которые менялись
- результаты

### Модуль / фича 2
- ...

## Найденные баги по дороге
- баг X: симптом, причина, фикс

## Изменённые файлы (итого)
- path1
- path2

## Следующее
- что планируется

## Связанное
- [[knowledge/decisions/...]]
- [[knowledge/debugging/...]]
```

## Уровень 3 — Долгосрочная память (knowledge base)

**Где**: тот же vault, папки `knowledge/` и при желании отдельные специализированные vault'ы.

**Структура `knowledge/`**:
```
knowledge/
  decisions/      ← архитектурные решения (почему выбрали X)
  debugging/      ← найденные баги и их фиксы (для будущего поиска)
  nodes/          ← документация компонентов (для трейдинга — узлы)
  patterns/       ← повторяющиеся паттерны, гайды
  phase-examples/ ← визуальные примеры (скриншоты, графики)
```

**Заметки в `decisions/`** — вечнозелёные:
```markdown
---
tags: [decision, architecture, <домен>]
date: 2026-04-10
---

# <Название решения>

## Контекст
Что было до, почему понадобилось решение. Альтернативы которые рассматривали.

## Решение
Конкретно что выбрали и как реализовали.

## Изменённые файлы
Список с путями.

## Что НЕ сделано (сознательно)
Что отложили на потом, почему.

## Риски и ограничения
Известные нюансы.

## Будущее
Что планируется развить из этого решения.
```

**Заметки в `debugging/`** — находки багов:
```markdown
---
tags: [debugging, <модуль>, critical]
date: 2026-04-10
---

# <Название бага>

## Симптом
Что было видно пользователю / в логах.

## Корневая причина
Реальная причина (часто не совпадает с симптомом).

## Диагностика
Как дошли до причины (для воспроизведения в будущем).

## Фикс
Что конкретно изменили.

## Урок
Что запомнить на будущее.
```

## Специализированные vault'ы (опционально)

Для больших проектов — **отдельные vault'ы по типу знания**:

```
C:\Users\admin\
  SolbotVault\         ← основной (всё выше)
  SolbotArchitecture\  ← только техническая архитектура
  SolbotLogic\         ← бизнес-логика по этапам (01-данные, 02-анализ, ...)
  SolbotNodes\         ← документация компонентов (узлов)
```

Это разделение полезно когда:
- У заметок разная аудитория (разработчик vs аналитик)
- Нужно расшаривать с коллегой только часть
- Заметок стало сильно больше 100 и поиск тяжёлый

## Workflow — как всё это использовать

### При старте новой сессии
Claude **обязательно** читает:
1. `CLAUDE.md` в корне проекта (автоматически)
2. Все файлы из `memory/` Уровня 1
3. `00-home/index.md` и `00-home/текущие приоритеты.md` Уровня 2
4. Последние 2-3 сессии из `sessions/`
5. Если задача касается модуля — соответствующую заметку из `knowledge/`

При команде **"продолжаем"** — то же самое, без уточняющих вопросов.

### Во время работы
- Большие решения → сразу черновик в `knowledge/decisions/`
- Найденный баг → черновик в `knowledge/debugging/`
- Важное pref / правило → в `memory/feedback_*.md` Уровня 1

### При команде "сохрани всё"
Пройти чек-лист (аналог `feedback_save_workflow.md`):

1. **Vault Уровня 2**: обновить `текущие приоритеты.md`, создать сессию `sessions/сессия YYYY-MM-DD тема.md`
2. **Vault Уровня 3**: добавить заметки в `decisions/` и `debugging/` для новых решений и багов
3. **Специализированные vault'ы** (если есть): обновить архитектуру/логику/компоненты
4. **Уровень 1 (memory Claude)**: обновить `project_status.md`, добавить новые `feedback_*.md` если появились правила, обновить индекс `MEMORY.md`
5. **Деплой** (если применимо): залить код на сервер

### При команде "сохрани сессию"
Минимальный вариант:
1. Создать `sessions/сессия YYYY-MM-DD тема.md`
2. Обновить `текущие приоритеты.md`
3. Если решение — заметка в `knowledge/decisions/`
4. Если баг — заметка в `knowledge/debugging/`
5. Обновить `index.md` если появились значимые новые заметки

## Критичные правила

### Уровень 1 (память Claude)
- **НЕ хранить** сессионный контекст — это Уровень 2
- **НЕ хранить** детали решений — это Уровень 3
- **Хранить**: кто пользователь, как работать, куда смотреть

### Уровень 2 (home + sessions)
- `текущие приоритеты.md` обязан быть актуальным — это "живой" документ
- Сессии не переписываем задним числом — это история
- Ссылки на Уровень 3 через `[[wiki-links]]`

### Уровень 3 (knowledge)
- Заметки вечнозелёные — формулировки в настоящем времени (не "вчера сделали X", а "X реализовано через Y")
- Один файл — одна концепция. Не складывать 5 решений в один файл
- Ссылки между заметками через `[[wiki-links]]`

## Пример чек-листа для `~/.claude/CLAUDE.md`

```markdown
# CLAUDE.md

## Язык
Всегда общайся на русском.

## Проект
<Название проекта и что он делает>
Основной код: <путь>
Сервер: <IP / SSH>

## Obsidian Knowledge Vault
Хранилище: <путь к основному vault>

### При старте сессии
Прочитай:
1. `memory/` (авто)
2. `00-home/index.md`
3. `00-home/текущие приоритеты.md`
4. Последние 2-3 сессии из `sessions/`
5. Если задача касается модуля — заметку из `knowledge/`

### При "сохрани всё"
Пройти 6 пунктов чек-листа (см. `feedback_save_workflow.md` в memory).

### При "сохрани сессию"
Пройти 5 пунктов короткого чек-листа (см. выше).
```

## Частые ошибки новичков

1. **Всё складывать в Уровень 1 (память Claude)** — контекст тонет. Правило: если это больше 2-3 строк — в vault.

2. **Не разделять сессии и решения** — когда решение описано в сессии, через месяц его не найти. Всегда выносить в `knowledge/`.

3. **Переписывать сессии "чтобы чище"** — теряется история как реально шла работа. Сессия = archive, не редактируется.

4. **Не ссылаться `[[wiki-links]]`** — заметки не связаны, Obsidian не помогает в навигации. Всегда добавлять взаимные ссылки.

5. **Забывать обновлять `текущие приоритеты.md`** — это живой центр Уровня 2. Устарел за неделю — ты не помнишь где остановился.

6. **Хранить секреты в vault** — пароли, API ключи никогда не попадают в Obsidian. Только ссылки "ключ в `.env` на сервере".

## Что проверить после настройки

- [ ] Папки `memory/`, `00-home/`, `sessions/`, `knowledge/` созданы
- [ ] `MEMORY.md` индекс есть и не пустой
- [ ] `CLAUDE.md` в корне проекта содержит ссылки на vault
- [ ] `00-home/index.md` описывает структуру проекта
- [ ] `00-home/текущие приоритеты.md` заполнен хотя бы на 1 задачу
- [ ] Хотя бы одна тестовая сессия создана по шаблону
- [ ] Проверено: "продолжаем" работает без уточняющих вопросов
- [ ] Проверено: "сохрани сессию" создаёт все нужные файлы

## Расширения

- **Git-версионирование vault** — папку vault-а закоммитить в приватный GitHub. История изменений + бэкап.
- **Obsidian Sync / iCloud / Dropbox** — доступ с разных устройств.
- **Templater plugin** — шаблоны для быстрого создания сессий/решений.
- **Dataview plugin** — автосписки "все решения за месяц", "все баги по тэгу".
- **Tags** — `[status, active], [session], [decision, architecture]` — для фильтрации.
